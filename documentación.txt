📘 Capítulo: Desarrollo del Sistema de Generación de Redes Virtuales Inteligentes con Terraform y Django

1. Introducción

El desarrollo presentado corresponde al módulo backend y frontend del sistema de simulación y despliegue de redes virtuales (VPCs), cuyo objetivo es permitir a los usuarios diseñar y desplegar redes AWS completas de forma visual mediante un canvas interactivo.

Cada elemento del canvas (VPC, subred, router, instancia, enlace, etc.) se traduce en una estructura JSON que describe la topología.
Esa estructura es luego interpretada por el backend, que genera automáticamente código Terraform, lo ejecuta en un entorno controlado y despliega la infraestructura real en AWS.

⸻

2. Objetivo general del sistema

Desarrollar una plataforma educativa y experimental que:
	•	Permita crear, editar y visualizar redes virtuales complejas a través de una interfaz gráfica.
	•	Genere y aplique configuraciones Terraform de manera automatizada desde un backend Python/Django.
	•	Permita realizar pruebas seguras, con simulaciones o despliegues reales, bajo un entorno de control.

⸻

3. Arquitectura general del sistema

La arquitectura se compone de tres capas principales:

3.1 Frontend (React + Canvas)
	•	Implementado con React y React Flow.
	•	Permite crear nodos (VPCs, subnets, routers, instancias) y enlaces entre ellos.
	•	Cada nodo guarda su configuración (CIDR, región, tipo, etc.).
	•	Al presionar “Deploy”, el sistema:
	•	Convierte la topología en un JSON estructurado.
	•	Envía ese JSON al backend para su procesamiento.

3.2 Backend (Django + Celery + Terraform)
	•	Django maneja la API REST y la base de datos de planes (“plans”).
	•	Cada Plan representa un despliegue o simulación.
	•	Al recibir el JSON, se ejecuta una tarea Celery (process_network_plan) que:
	1.	Renderiza el archivo main.tf.j2 con la plantilla de Terraform.
	2.	Crea un directorio temporal (/tmp/tf-multi-*) y guarda los archivos generados.
	3.	Ejecuta los comandos terraform init, terraform plan y terraform apply (si es un despliegue real).
	4.	Registra logs completos y estados en la base de datos y/o S3.

3.3 Capa de infraestructura (Terraform + AWS)
	•	Terraform es el motor declarativo que interpreta la plantilla generada (main.tf).
	•	Se crean recursos como:
	•	VPCs, Subnets, Internet Gateways (IGW), NAT Gateways, Route Tables, Instances (EC2), Transit Gateways (TGW) y VPC Peering Connections.
	•	Los recursos se destruyen mediante un proceso automatizado con un botón “Destroy” desde la interfaz.

5. Descripción funcional actual

5.1 Desde el punto de vista del usuario
	1.	El usuario abre el canvas y diseña una red:
	•	Crea una o varias VPCs.
	•	Dentro de ellas, define subnets (públicas o privadas).
	•	Puede agregar routers (TGW) y definir conexiones (peering o attach).
	•	Añade instancias dentro de las subnets, configurando IPs, llaves SSH, etc.
	2.	Presiona “Deploy”:
	•	El frontend genera un JSON con toda la topología.
	•	Ese JSON se envía al backend (endpoint /api/network/plan/).
	•	Se crea un registro Plan en la base de datos y una tarea Celery asíncrona se encarga de ejecutar Terraform.
	3.	Desde el panel “Plans” puede:
	•	Ver el estado (PENDING, RUNNING, SUCCESS, FAILURE).
	•	Ver logs detallados de la ejecución de Terraform.
	•	Re-lanzar el plan (deploy real o simulado).
	•	Destruir la infraestructura desplegada (botón “Destroy”).

6. Estructura y flujo de datos

6.1 Estructura JSON base enviada desde el canvas

{
  "name": "Test Network",
  "simulate_only": false,
  "vpcs": [
    {
      "id": "vpcA",
      "name": "VPC-A",
      "region": "us-east-1a",
      "cidr_block": "10.10.0.0/16",
      "internet_gateway": true,
      "nat_gateway": { "enabled": true, "public_subnet": "pub-a1" },
      "route_tables": [
        { "name": "public",  "routes": [{ "target": "igw", "dest_cidr": "0.0.0.0/0" }] },
        { "name": "private", "routes": [{ "target": "nat", "dest_cidr": "0.0.0.0/0" }] }
      ],
      "subnets": [
        { "name": "pub-a1", "cidr_block": "10.10.1.0/24", "map_public_ip_on_launch": true, "route_table": "public" },
        { "name": "priv-a1", "cidr_block": "10.10.2.0/24", "map_public_ip_on_launch": false, "route_table": "private" }
      ]
    }
  ],
  "routers": [{ "id": "core", "type": "tgw", "name": "Core-TGW" }],
  "links": [
    { "type": "tgw-attach", "router_id": "core", "vpc_id": "vpcA", "subnet_names": ["priv-a1"] }
  ]
}

6.2 Ejecución Terraform paso a paso
	1.	Django recibe el JSON → Renderiza main.tf.j2.
	2.	Se crea un directorio temporal con:

main.tf
plan.out
_received_plan.json
_main_preview.txt


	3.	Se ejecutan los comandos:

terraform init
terraform plan (si simulate_only=true)
terraform apply (si simulate_only=false)


	4.	Tras apply, se ejecuta terraform output -json para capturar outputs definidos en main.tf.j2.
	5.	Los logs, estado y outputs se guardan en la base de datos y/o en S3.
	6.	El estado Terraform se persiste localmente en volumen /tfstate, permitiendo que destroy sea reproducible y consistente.

7. Principios de diseño aplicados
	•	Desacoplamiento:
La lógica de infraestructura (Terraform) está completamente separada del backend de control (Django).
	•	Escalabilidad:
El uso de Celery + Redis permite ejecutar múltiples despliegues en paralelo sin bloquear el servidor principal.
	•	Extensibilidad:
La plantilla main.tf.j2 es dinámica: interpreta cualquier estructura JSON que cumpla la forma esperada, permitiendo que el canvas evolucione (añadir nuevos tipos de nodos o relaciones).
	•	Reproducibilidad:
Cada despliegue genera archivos temporales reproducibles y logs auditables, lo que permite volver a ejecutar el mismo plan o destruirlo completamente.
	•	Seguridad:
Los despliegues reales (simulate_only=false) solo se permiten cuando hay credenciales IAM configuradas o se ejecuta dentro de un entorno autorizado (ECS/Render). Se bloquea apply y destroy si no existen credenciales válidas.
	•	Instrumentación:
La opción B de main.tf.j2 incluye outputs declarados que capturan información clave tras apply, los cuales se almacenan en el campo Plan.outputs luego de ejecutar terraform output -json.
	•	Orquestación:
Celery actúa como orquestador real del ciclo de vida Terraform, gestionando estados, logs, y secuencia de comandos init → plan → apply → output → destroy.

8. Resultados alcanzados

El sistema actualmente permite:
	•	Simular y desplegar topologías multi-VPC completas con una clara diferenciación entre simulate_only=true (plan) y simulate_only=false (apply real).
	•	Crear recursos AWS con un solo click desde el canvas, con persistencia local del estado Terraform en volumen /tfstate, lo que garantiza que las operaciones destroy sean reproducibles y coherentes.
	•	Desplegar o destruir infraestructuras reproducibles mediante comandos terraform apply y terraform destroy controlados desde la UI.
	•	Generar código Terraform automáticamente sin escribirlo manualmente, usando la plantilla modular main.tf.j2 opción B que incluye outputs para captura de datos post-aplicación.
	•	Registrar y almacenar outputs en el campo Plan.outputs, llenado tras ejecutar terraform output -json, facilitando análisis y auditoría de los recursos creados.
	•	Controlar estrictamente la seguridad, bloqueando operaciones apply y destroy si no existen credenciales IAM válidas, previniendo despliegues no autorizados.
	•	Orquestar el ciclo completo de vida Terraform mediante Celery, que gestiona la creación, planificación, aplicación, captura de outputs y destrucción de infraestructuras.
	•	Proveer un sistema de logging avanzado y persistente, con estados almacenados en la base de datos y posibilidad de integración futura con S3 para almacenamiento remoto del estado y logs.

10. Conclusión del estado actual

A este punto, el sistema ha evolucionado de un prototipo de simulación a una plataforma funcional de despliegue de redes en AWS.
La arquitectura modular, el uso de plantillas dinámicas y la integración de Celery permiten una automatización total del ciclo de vida de infraestructura.

Además, la estructura es escalable y educativa: cada paso del despliegue es visible, registrable y explicable, lo que hace que este proyecto no solo tenga un valor técnico, sino también didáctico y científico, al conectar la programación visual con la infraestructura como código (IaC).

11. Estado técnico validado (enero 2026)

Para enero de 2026, se ha validado que el sistema cumple con los siguientes aspectos técnicos:

- La plantilla main.tf.j2 opción B está completamente instrumentada con outputs que permiten extraer información clave de los recursos desplegados, facilitando la trazabilidad y auditoría.
- La persistencia del estado Terraform en un backend local montado en volumen /tfstate garantiza que las operaciones destroy sean reproducibles y consistentes, evitando pérdidas o inconsistencias en el estado.
- La distinción clara entre simulate_only=true (ejecución de terraform plan sin aplicar cambios) y simulate_only=false (terraform apply real) está implementada y controlada, asegurando que el usuario pueda elegir entre simulación y despliegue efectivo.
- El campo Plan.outputs se llena automáticamente tras cada apply mediante la ejecución de terraform output -json, almacenando toda la información relevante para análisis posteriores.
- El ciclo completo de vida de un plan (create plan → plan → apply → outputs → destroy) está orquestado mediante Celery, que maneja estados, logs, y validaciones de seguridad.
- Se ha reforzado la seguridad bloqueando la ejecución de apply y destroy cuando no se detectan credenciales IAM válidas, evitando despliegues o destrucciones no autorizadas.
- La interfaz de usuario refleja en tiempo real el estado de ejecución mediante polling al backend, mejorando la experiencia y transparencia del proceso.
- El sistema está preparado para evolucionar hacia la persistencia del estado Terraform en almacenamiento remoto (S3), lo que permitirá escalabilidad y colaboración multiusuario.

Este estado técnico validado confirma que la plataforma es apta para uso académico y experimental, con un diseño robusto que puede ser base para futuras extensiones y mejoras.
