📘 Capítulo: Desarrollo del Sistema de Generación de Redes Virtuales Inteligentes con Terraform y Django

1. Introducción

El desarrollo presentado corresponde al módulo backend y frontend del sistema de simulación y despliegue de redes virtuales (VPCs), cuyo objetivo es permitir a los usuarios diseñar y desplegar redes AWS completas de forma visual mediante un canvas interactivo.

Cada elemento del canvas (VPC, subred, router, instancia, enlace, etc.) se traduce en una estructura JSON que describe la topología.
Esa estructura es luego interpretada por el backend, que genera automáticamente código Terraform, lo ejecuta en un entorno controlado y despliega la infraestructura real en AWS.

⸻

2. Objetivo general del sistema

Desarrollar una plataforma educativa y experimental que:
	•	Permita crear, editar y visualizar redes virtuales complejas a través de una interfaz gráfica.
	•	Genere y aplique configuraciones Terraform de manera automatizada desde un backend Python/Django.
	•	Permita realizar pruebas seguras, con simulaciones o despliegues reales, bajo un entorno de control.

La arquitectura se compone de tres capas principales:


3.1 Frontend (React + Canvas)

3.1.1 Sincronización determinística entre Canvas y Plan Validado (Hash-based)

Durante esta etapa del desarrollo se implementó un mecanismo determinístico de sincronización entre el estado visual del canvas y el último plan validado.

Problema resuelto:
Anteriormente, el estado "PLAN: VALIDADO" dependía únicamente de estados en memoria (validationState), lo que generaba inconsistencias tras refrescar la página.

Solución implementada:
Se incorporó un sistema de verificación basado en hash estructural de infraestructura:

• Se creó la función computeInfraHash(nodes, edges) en infraHash.js.
• El hash se genera a partir del resultado de buildRoutingPreview, lo que garantiza que solo la infraestructura relevante impacte el cálculo.
• Al validar un plan, se persiste en Firestore:
  - planId
  - planCanvasHash
  - planValidationOk
• Al restaurar el canvas tras un refresh, el sistema:
  1. Reconstruye el hash actual desde nodes y edges.
  2. Lo compara con planCanvasHash almacenado.
  3. Deriva el estado visual sin depender de memoria de sesión.

Reglas actuales de sincronización:
• Si existe planCanvasHash y el hash coincide → estado visual: PLAN_VALIDATED.
• Si existe planCanvasHash y el hash difiere → estado visual: PLAN_OUTDATED.
• Si no existe planCanvasHash → estado visual: NO_PLAN.


Este enfoque garantiza consistencia tras refresh, evita falsos "DESACTUALIZADO" y elimina dependencias frágiles de efectos React ejecutados antes de terminar la restauración del flujo.

---

3.1.2 Diagrama conceptual del ciclo de coherencia

El ciclo lógico completo de coherencia entre el Canvas y el Plan validado puede representarse como:

Canvas (nodes, edges)
        ↓
buildRoutingPreview()
        ↓
computeInfraHash()
        ↓
Persistencia en Firestore
(planId + planCanvasHash + planValidationOk)
        ↓
Refresh / Restauración del flujo
        ↓
Re-cálculo de computeInfraHash()
        ↓
Comparación estructural
        ↓
Derivación de estado visual
(PLAN_VALIDATED / PLAN_OUTDATED / NO_PLAN)

Este flujo garantiza que el estado visual nunca dependa exclusivamente de memoria de sesión, sino de una comparación determinística basada en la infraestructura representada.

El sistema se aproxima así a un modelo declarativo puro donde:

Estado visual = f(Canvas actual, Plan persistido)

Lo que refuerza la coherencia académica y técnica del sistema como herramienta educativa de Infraestructura como Código (IaC).

3.2 Backend (Django + Celery + Terraform)
	•	Django maneja la API REST y la base de datos de planes (“plans”).
	•	Modelo actual (Camino 1): 1 Plan = 1 stack. Cada Plan representa una única infraestructura (stack Terraform) asociada a un state persistente. El plan puede ejecutarse múltiples veces (deploy o destroy), pero siempre reutiliza el mismo state y apunta al mismo conjunto de recursos.
	•	Al recibir el JSON, se ejecuta una tarea Celery (process_network_plan) que:
	1.	Renderiza el archivo main.tf.j2 con la plantilla de Terraform.
	2.	Crea un directorio temporal (/tmp/tf-multi-*) y guarda los archivos generados.
	3.	Ejecuta los comandos terraform init, terraform plan y terraform apply (si es un despliegue real).
	4.	Registra logs completos y estados en la base de datos. (La integración con S3 queda preparada para una fase futura, pero no se usa en el estado actual del sistema).

3.2.1 Entorno DEV con Docker Compose
    • Se estandarizó el entorno local con `tools/docker/compose.dev.yml` (frontend, backend, celery, redis, postgres, flower).
    • El backend y celery montan:
      - /tfstate y /tfwork como volúmenes para persistir estado y directorios de trabajo.
      - ~/.aws dentro del contenedor (solo lectura) para usar perfiles AWS sin exponer claves en .env.
    • Variables clave usadas en DEV:
      - HOME=/home/app
      - AWS_SDK_LOAD_CONFIG=1
      - AWS_PROFILE=<perfil>
      - AWS_DEFAULT_REGION=us-east-1
      - ALLOW_LOCAL_APPLY=1
    • Healthchecks: backend expone /healthz, postgres usa pg_isready, redis usa redis-cli ping, celery usa inspect ping.

3.3 Capa de infraestructura (Terraform + AWS)

6.1.1 Persistencia y verificación de coherencia del Plan (Frontend)

El frontend ahora implementa un mecanismo de coherencia basado en comparación estructural.

Flujo resumido:
1. El usuario valida un plan.
2. El backend devuelve planId y el frontend calcula computeInfraHash.
3. Ese hash se guarda en Firestore como planCanvasHash.
4. En cada modificación del canvas (nodes o edges), el sistema recalcula el hash.
5. Si el hash actual difiere del persistido, el canvas entra en estado PLAN_OUTDATED.

Importante:
• El estado "PLAN: VALIDADO" ya no depende de validationState en memoria.
• El estado visual es derivado, no almacenado.
• Esto permite que al recargar la página el sistema reconstruya correctamente el estado del plan sin intervención del usuario.

Este diseño aproxima el comportamiento del sistema a un modelo declarativo puro donde la infraestructura validada es una función determinística del estado del canvas.

6.2 Ejecución Terraform paso a paso
	1.	Django recibe el JSON → Renderiza main.tf.j2.
	2.	Se crea un directorio temporal con:

main.tf
plan.out
_received_plan.json
_main_preview.txt


	3.	Se ejecutan los comandos:

terraform init
terraform plan
terraform apply (solo si simulate_only=false)
terraform output -json (solo después de apply)
terraform destroy (cuando se llama Destroy y simulate_only=false)


	4.	Tras apply, se ejecuta terraform output -json para capturar outputs definidos en main.tf.j2.
	5.	Los logs, estado y outputs se almacenan en la base de datos del Plan (Plan.last_log y Plan.outputs).
	6.	El estado Terraform se persiste localmente en /tfstate/<plan_id>/terraform.tfstate, garantizando que las operaciones destroy sean reproducibles y coherentes para ese mismo Plan.
5.2 Reglas de ejecución, consistencia y control de concurrencia (HTTP 409)

Para evitar estados inconsistentes o corrupción del state de Terraform, el sistema impone una regla estricta:

• Un Plan solo puede tener una ejecución activa a la vez.

Implementación técnica:
• Al iniciar un Deploy o Destroy, el backend valida si el Plan se encuentra en estado RUNNING.
• Si existe una ejecución en curso, la API responde HTTP 409 Conflict con el mensaje:
  "Plan en ejecución. Espera a que termine antes de lanzar otra acción."
• La respuesta incluye el task_id activo para trazabilidad y depuración.

Motivación técnica:
• Terraform utiliza un state como fuente única de verdad.
• Ejecutar apply/destroy concurrentes sobre el mismo state puede provocar locks inconsistentes, recursos huérfanos o destrucciones parciales.
• Bajo el modelo Camino 1 (1 Plan = 1 stack), todas las ejecuciones reutilizan el mismo state ubicado en /tfstate/<plan_id>/terraform.tfstate.

Impacto en la experiencia de usuario (UX):
• Si el usuario intenta ejecutar una acción mientras otra está en curso, la interfaz muestra un aviso claro de "Plan en ejecución".
• Las acciones quedan deshabilitadas hasta que la ejecución finaliza.
• El task_id visible permite seguir el progreso y entender exactamente qué proceso está en marcha.

Resultado:
• Deploy y Destroy se convierten en operaciones deterministas.
• Se garantiza que cada acción afecta siempre al mismo stack del Plan.
• Se elimina el riesgo de recursos AWS huérfanos por concurrencia.

7. Principios de diseño aplicados
	•	Desacoplamiento:
La lógica de infraestructura (Terraform) está completamente separada del backend de control (Django).
	•	Escalabilidad:
El uso de Celery + Redis permite ejecutar múltiples despliegues en paralelo sin bloquear el servidor principal.
	•	Extensibilidad:
La plantilla main.tf.j2 es dinámica: interpreta cualquier estructura JSON que cumpla la forma esperada, permitiendo que el canvas evolucione (añadir nuevos tipos de nodos o relaciones).
	•	Reproducibilidad:
Cada despliegue genera archivos temporales reproducibles y logs auditables, lo que permite volver a ejecutar el mismo plan o destruirlo completamente.
	•	Seguridad:
Seguridad: Los despliegues reales (simulate_only=false) y el destroy solo se permiten cuando el entorno está autorizado. En local: requiere ALLOW_LOCAL_APPLY=1 y credenciales válidas vía AWS profile montado (AWS_SDK_LOAD_CONFIG=1 + AWS_PROFILE) o claves estáticas. En producción: permitido por task role (ECS/Render).
	•	Instrumentación:
La opción B de main.tf.j2 incluye outputs declarados que capturan información clave tras apply, los cuales se almacenan en el campo Plan.outputs luego de ejecutar terraform output -json.
	•	Orquestación:
Celery actúa como orquestador real del ciclo de vida Terraform, gestionando estados, logs, y secuencia de comandos init → plan → apply → output → destroy.
	•	Claridad semántica (UX-first):
  	La interfaz distingue explícitamente entre “plan”, “ejecución” y “estado de infraestructura”, evitando confusión entre logs, botones o estados. 
  	Esto permite escalar el sistema sin romper el modelo mental del usuario.

12. Síntesis estructural del proyecto (Base para libro técnico)

12.1 ¿Qué hace este proyecto?

Este proyecto es una plataforma web que permite modelar redes virtuales en AWS de forma visual y transformarlas automáticamente en infraestructura real utilizando Terraform.

El sistema:
• Permite diseñar topologías de red mediante un canvas interactivo.
• Valida la coherencia estructural de la red antes del despliegue.
• Genera dinámicamente código Terraform basado en la topología.
• Ejecuta terraform plan / apply / destroy desde un backend controlado.
• Persiste estado, logs y outputs para trazabilidad.
• Permite diferenciar entre simulación (plan) y despliegue real (apply).

No es un simulador estático. Es un sistema de Infraestructura como Código (IaC) asistido por interfaz gráfica.

⸻

• Backend local de estado Terraform en volumen /tfstate

12.3 Reglas fundamentales del sistema

1. 1 Plan = 1 Stack
   Cada Plan corresponde a un único estado Terraform persistido en:
   /tfstate/<plan_id>/terraform.tfstate

2. No hay ejecuciones concurrentes
   Si un Plan está en RUNNING → HTTP 409.

3. Estado visual derivado
   PLAN_VALIDATED / PLAN_OUTDATED / NO_PLAN se deriva de:
   computeInfraHash(canvas) vs planCanvasHash persistido.

4. No existe conectividad implícita
   Toda ruta debe declararse explícitamente.
   Las rutas asimétricas generan advertencia.

5. simulate_only controla el comportamiento:
   • true  → terraform plan
   • false → terraform apply real

6. Destroy solo opera sobre el mismo state del Plan.

12.4 Funcionamiento de los escenarios principales

Escenario 1 — VPC pública
• Se declara 0.0.0.0/0 → igw.
• Backend genera IGW + route table pública.
• Subnet con map_public_ip_on_launch = true.
• Terraform crea conectividad real a Internet.

Escenario 2 — Peering entre VPCs
• Se declaran rutas simétricas.
• Backend genera aws_vpc_peering_connection.
• Se crean rutas cruzadas automáticamente.

Escenario 3 — Ruta asimétrica
• Solo una VPC declara ruta.
• Preview genera warning ASYMMETRIC_ROUTE.
• Se evita despliegue inconsistente.

Escenario 4 — Router lógico (TGW conceptual)
• Se modela hub-and-spoke.
• Links tipo tgw-attach.
• Backend traduce intención en recursos TGW (cuando está habilitado).
• Escalable a múltiples VPCs.

Docker DEV:

12.6 Lógica arquitectónica seguida

El sistema sigue una lógica declarativa y determinística:

1. El usuario diseña infraestructura.
2. Se genera preview estructural.
3. Se calcula hash de infraestructura.
4. Se valida coherencia.
5. Se persiste plan.
6. Celery ejecuta Terraform.
7. Se capturan outputs.
8. Se actualiza estado del Plan.
9. El estado visual se deriva del hash comparado.

Modelo conceptual:

Infraestructura real = f(Canvas validado)

El estado no depende de memoria de sesión, sino de comparación estructural persistida.

12.7 Nivel actual del sistema

El sistema se encuentra en estado MVP funcional avanzado:

• Deploy y Destroy real validados end-to-end.
• Persistencia determinística del estado.
• Validación topológica previa al despliegue.
• Arquitectura extensible.
• Separación clara entre lógica visual, backend de control e infraestructura declarativa.

Es técnicamente apto para defensa de tesis y sirve como base sólida para evolucionar hacia un producto enterprise.
